# R3 Currencies Experiment - branch `experiment/r3-currencies` - AI-Generated, Unreviewed Text

This branch contains an experiment that replaced the currency change event flow with R3 reactive properties.

This text was generated by AI and was not reviewed by the project owner. Treat it as a working note for this branch only, not as project documentation for `main`.

## What Was Changed

The currency wallet API was changed from a generic `Changed` event plus `Get(CurrencyType)` reads to explicit read-only reactive properties:

- `SoftCurrency`
- `HardCurrency`

`PlayerStateCurrenciesGateway` now owns private `ReactiveProperty<int>` instances and exposes them as `ReadOnlyReactiveProperty<int>`. `CurrenciesService` forwards those properties to consumers. The currencies debug page subscribes directly to the properties instead of subscribing to a general `Changed` event and then refreshing both displayed values.

## Bug Found During The Experiment

The first implementation introduced a second state layer in `PlayerStateCurrenciesGateway`.

`PlayerStateProvider` remained the real source of truth, while `PlayerStateCurrenciesGateway` cached currency values in `ReactiveProperty<int>`. This cache was updated on direct currency writes, but it did not update after player state reset. As a result, after resetting player state and opening the currencies debug page, the old currency values could still be displayed until the application restarted or a currency button was pressed.

The branch now adds `IPlayerStateProvider.Refreshed` and uses it to resynchronize the currency reactive properties after `PlayerStateProvider.Refresh()`.

## Assessment

The experiment did not produce a convincing simplification for currencies.

Benefits:

- UI can subscribe to a specific value instead of a generic change event.
- Initial values are pushed on subscription.
- The approach could be useful for derived UI state if the source state is already reactive.

Costs:

- Currency state now exists in both `PlayerStateProvider` and `PlayerStateCurrenciesGateway`.
- Cache synchronization must be handled manually across multiple state lifecycle events.
- The public currency contract now depends on R3.
- Tests became more awkward because Editor-only test assemblies do not currently reference the R3 DLL directly.
- `TryAdd` and `TrySpend` remain imperative commands, so the core currency logic did not become meaningfully more reactive.

## Conclusion

This branch should be treated as an experiment, not as a recommended implementation.

For this project architecture, applying R3 directly inside `PlayerStateCurrenciesGateway` appears to be the wrong integration point. If R3 is introduced later, a better direction would be to make the player state layer itself publish state changes, then derive currency observables from that single source of truth. Another reasonable use case is local UI state where `ReactiveProperty<T>` is the actual owner of the value rather than a cache of another model.

Unless the player state architecture is changed first, the old currency implementation is likely preferable for `main`.
